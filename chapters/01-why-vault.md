# 第 1 章 为什么需要 Vault：一个泄露事故的复盘

## 需求

先不谈工具。假设你入职"北极星电商"的第一周，收到一张工单：

> **【P1】线上订单库的连接串疑似外泄，请立刻更换全站数据库密码。**
> 工单附件是一张截图：某位离职同事的公开 GitHub 仓库里，`config/prod.yml` 明文写着 `DATABASE_URL=mysql://appuser:Pr0d%40123@db.prod.internal:3306/orders`。

你要在周末之前回答三个问题：

1. 这个密码还有谁在用？（不知道。）
2. 换掉它会影响哪些服务？（得一个个翻配置。）
3. 换完之后，怎么保证下周不会再发生一次？（把密码加密后继续贴？）

这三个问题，就是 Vault 存在的理由。

## 动手：先看看"哪儿都存一份"到底是什么样子

在引入任何工具之前，我们先把手头这种做法的成本量化一下。真实事故里，凭据通常会同时出现在至少这些地方：

```text
① 代码仓库          config/prod.yml、docker-compose.yml、.env
② CI/CD 变量        GitHub Actions Secrets、Jenkins 凭据、GitLab CI Variables
③ 部署编排          K8s Secret、Ansible vault 文件、Helm values
④ 配置中心          Nacos / Apollo / Consul KV
⑤ 运维文档/聊天群     wiki、Confluence、截图、Excel、钉钉群文件
⑥ 开发者本机        ~/.bash_history、IDE 的 run configuration、临时脚本
⑦ 备份与快照        DB dump、镜像层、日志
```

数一数：一次轮换要改 7 个地方。漏一个，泄露面就还在。

## 原理：四个必须回答的问题

不管用什么方案，凭据管理都得回答四个问题。Vault 的设计，就是把这四个问题拆成四类可独立演进的组件：

| 问题 | Vault 的答案 | 章节 |
| --- | --- | --- |
| 密钥**存**在哪？ | Secrets Engine（密钥引擎），可挂载、可版本化 | 第 4、6、10、11 章 |
| 谁**能读**？ | Policy（策略）+ Token（令牌） | 第 5、7 章 |
| 怎么证明"我是谁"？ | Auth Method（认证方法） | 第 8、9 章 |
| 出了事怎么**知道**和**回收**？ | Audit Device（审计设备）+ Lease（租约） | 第 12、13 章 |

用生活里的物件打个比方，这套映射会很好记：

```text
Secrets Engine  保险柜（可以有很多个，各自装不同东西）
Auth Method     门口的证件核验（工牌 / 指纹 / 访客码）
Policy          一张写着"你能开哪几个柜子、能做什么"的权限单
Token           一次性通行证，有效期到点作废
Lease           通行证和临时物品的租期，到期自动收回
Audit Device    门口的监控摄像头（记录谁在什么时候碰了什么）
```

一次典型的请求会这样流动：

```text
客户端 ──(1) 带凭证登录 auth/<方法> ──▶ Vault
                                          │  核验身份，生成 Token（带上策略）
客户端 ◀──(2) Token ─────────────────────┘
客户端 ──(3) 带 Token 请求 <引擎>/data/... ──▶ Vault
                                          │  ① 查策略：这个路径允许 read 吗？
                                          │  ② 查引擎：数据取出来
                                          │  ③ 写审计日志（请求+响应）
                                          │  ④ 若是动态密钥：登记一条 Lease
客户端 ◀──(4) 数据 ──────────────────────┘
```

关键在于第 (3) 步走的是**同一条路径**：任何引擎、任何客户端，都要过策略检查和审计记录。这就是"集中管理"真正的含义——不是把密码放到另一个地方，而是把**所有读取动作收进一个可检查的关口**。

## 回到事故：Vault 能改变什么

把第一幕的需求逐条对应到方案：

**需求 1：密码集中存，且能版本回滚。**
用 KV v2 引擎存 `orders/db`，每次写入产生一个版本。写错了可以直接回滚到上一版，不需要把密码抄在便签上。→ 第 4 章

**需求 2：只有订单服务和 DBA 能读这个密码，其他人一律拒绝。**
用策略把路径和权限写死，并且**默认拒绝**。谁能读、谁能写变成一份可以 code review 的文件。→ 第 5 章

**需求 3：轮换之后不用改 7 个地方。**
更好的答案是：**根本不要有长期密码**。让 Vault 在应用启动时向数据库申请一个 1 小时就过期的账号。密码不存在于任何配置文件里，也就没有"哪里漏了"的问题。→ 第 6 章

**需求 4：离职同事的仓库里就算躺着旧密码，也没用。**
动态密钥 + 短 TTL 让泄露的时间窗口从"永远"缩短到"一小时"。→ 第 6、12 章

**需求 5：事后能查清"谁在什么时候读走了什么"。**
审计设备把每一次请求和响应都记录下来（敏感值做 HMAC 处理）。→ 第 13 章

## 本书的推进路线

```text
第 1 章   你在读的这章：先建立"为什么"
第 2-4 章  把 Vault 跑起来 → 存第一个密钥 → 学会 KV v2 的版本与删除语义
第 5-9 章  策略 / Token / 认证方法 / Agent：解决"谁能读，机器怎么读"
第 10-13 章 Transit / PKI / 租约 / 审计：解决"密钥不该长期存在"和"合规"
第 14-17 章 生产三件事：Seal、存储与备份、上线检查清单
```

## 踩坑与检查清单

- **别把 Vault 当成"加密版的配置文件"。** 如果只是把密码加密后继续提交到 Git，问题只是从"明文泄露"变成"密钥泄露"，轮换成本一点没降。Vault 的价值在于**缩短凭据寿命**和**集中授权**。
- **先量化，再选型。** 动手前把上面那 7 个存放点列出来，标出哪些能靠动态密钥一次性消灭。你会发现收益最大的是"没人再手动分发密码"。
- **Vault 不是万能的。** 它不负责网络隔离、不负责主机安全、也不负责应用自己的越权逻辑。它负责的是凭据的存储、授权、轮换和审计。
- **别一上来就上生产。** 先用第 2 章的 dev 模式把手感练出来，再读第 14-16 章理解生产要求。
