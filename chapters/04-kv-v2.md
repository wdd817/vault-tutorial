# 第 4 章 KV v2：给密钥加上版本和删除保护

## 需求

> 运维同学在群里说："刚才手抖把生产环境的数据库密码覆盖成测试库的了，谁能找回来？"
> 你打开 Vault，发现里面只有**一个当前值**——没有任何历史。于是只能去数据库重置密码，再通知所有人。
>
> 我们要的是一个**像 Git 一样能回滚、像回收站一样能后悔**的密钥存储。

KV v2 就是为此设计的。本章把它彻底讲清楚：版本、CAS（乐观锁）、软删除、彻底销毁、元数据、以及权限路径的对应关系。

## 动手

### 4.1 挂载一个自己的 KV v2 引擎

别在老 `secret/` 上做实验，我们给"北极星电商"建一个业务专用的柜子：

```bash
vault secrets enable -path=app kv-v2
vault secrets list
```

```text
Success! Enabled the kv-v2 secrets engine at: app/

Path               Type              Accessor                   Description
----               ----              --------                   -----------
agent-registry/    agent_registry    agent-registry_c7e72d4b    agent registry
app/               kv                kv_965f051c                n/a
cubbyhole/         cubbyhole         cubbyhole_b06ffeee         per-token private secret storage
...
```

> **注意**：`vault secrets enable -path=app kv-v2` 里的 `kv-v2` 是**引擎类型**，也可以用别名 `kv` 并配合 `-version=2`。Vault 2.x 的默认 `secret/` 挂载就是 v2，所以教程里到处能看到 version 字段。

### 4.3 `put` 与 `patch`：整体替换 vs 局部修改

`vault kv put` 是**整体替换**：没写到的字段会消失。`vault kv patch` 才是局部更新：

```bash
# 注意：put 之后 username 字段没了
vault kv get -mount=app demo
# username 已经被"r0tated"那次 put 抹掉

# patch：只改 username，保留 password
vault kv patch -mount=app demo username=patched
vault kv get -mount=app demo
```

```text
====== Data ======
Key         Value
---         -----
password    r0tated
username    patched
```

这个差异是生产事故的常见来源：**用 `put` 做"只改一个字段"的意图操作**，会静默删掉其他字段。

### 4.4 CAS：防止两个人互相覆盖

CAS（Check-And-Set）就是密钥世界的乐观锁。它的规则只有一条：**写的时候如果"当前版本号"和你说好的不一样，就拒绝写入。**

```bash
vault kv metadata put -mount=app -cas-required=true demo
vault kv put -mount=app -cas=1 demo password=nope
```

```text
Error writing data to app/data/demo: Error making API request.

URL: PUT http://127.0.0.1:8200/v1/app/data/demo
Code: 400. Errors:

* check-and-set parameter did not match the current version
```

退出码是 2。加上正确的版本号就能写：

```bash
vault kv put -mount=app -cas=3 demo password=ok
```

**CAS 的两种用法**：

| 参数 | 语义 |
| --- | --- |
| `-cas=0` | 仅当 key **不存在**时才允许写（创建语义，防止覆盖别人） |
| `-cas=<n>` | 仅当当前版本是 `n` 时才允许写（更新语义） |
| `-cas-required=true` | 挂载级配置：所有写入都必须带 cas，防止"盲写" |

对"多副本服务同时刷新密钥"的场景，`cas-required` 能直接消灭一整类竞态 bug。

### 4.5 三种"删除"：别混淆

KV v2 的删除分三层，这是它最容易被误解的地方：

| 操作 | 命令 | 效果 | 能否恢复 |
| --- | --- | --- | --- |
| **软删除**（delete） | `vault kv delete` | 该版本标记为已删除，读不出来 | ✅ `undelete` 可恢复 |
| **彻底销毁**（destroy） | `vault kv destroy` | 该版本的数据被真正抹除 | ❌ 不可恢复 |
| **删除全部元数据** | `vault kv metadata delete` | 整个 key 及其所有版本、元数据一起消失 | ❌ 不可恢复 |

逐个实测：

```bash
# ① 软删除当前版本
vault kv delete -mount=app demo
vault kv get -mount=app demo
```

```text
== Secret Path ==
app/data/demo

======= Metadata =======
Key                Value
---                -----
created_time       2026-09-23T12:16:58.9577613Z
custom_metadata    <nil>
deletion_time      2026-09-23T12:16:59.257736Z
destroyed          false
version            4
```

注意：**命令退出码是 0，输出里没有 Data 段**，只有 metadata，`deletion_time` 有值。这不是"没找到"，而是"这个版本被标记删除了"。这一点很重要——很多脚本用"输出里有没有数据"判断存在性，会误判。

```bash
# ② 恢复（注意 -versions 是复数）
vault kv undelete -mount=app -versions=4 demo
vault kv get -mount=app -version=4 demo

# ③ 彻底销毁
vault kv destroy -mount=app -versions=1 demo
vault kv get -mount=app -version=1 demo
```

```text
======= Metadata =======
Key                Value
---                -----
created_time       2026-09-23T12:16:58.5289107Z
custom_metadata    <nil>
deletion_time      n/a
destroyed          true      ← 数据已抹除
version            1
```

```bash
# ④ 回滚：把某个历史版本的内容重新写成最新版本（产生新版本，不改变历史）
vault kv rollback -mount=app -version=2 demo

# ⑤ 整个 key 连元数据一起删除（对不存在的 key 也会回 Success!，所以先写入一次是为了能验证它真的消失了）
vault kv put -mount=app db/dev password=d1
vault kv metadata delete -mount=app db/dev
```

> **注意**：`vault kv metadata delete` 对**不存在**的 key 也会回 `Success! Data deleted (if it existed) at: ...`、退出码 0（实测连删两次都成功），所以"删没删掉"要看后续的 `list`/`get`，不能看这条命令的退出码。

### 4.6 元数据：版本数量上限、自定义元数据

`vault kv metadata` 是管理 key 生命周期的入口：

```bash
vault kv metadata put -mount=app -max-versions=3 -cas-required=true demo
vault kv metadata get -mount=app demo
```

```text
= Metadata Path =
app/metadata/demo

========== Metadata ==========
Key                     Value
---                     -----
cas_required            true
created_time            2026-09-23T12:16:58.5289107Z
current_version         5
custom_metadata         <nil>
delete_version_after    0s
last_updated_by         map[actor:token client_id:... operation:update]
max_versions            3
oldest_version          0
updated_time            2026-09-23T12:18:51.2059625Z

====== Version 1 ======
Key              Value
---              -----
created_by       {"actor":"token","client_id":"...","operation":"create"}
created_time     2026-09-23T12:16:58.5289107Z
deleted_by       <nil>
deletion_time    n/a
destroyed        true
```

> **说明**：上面是节选——实测这里会继续列出 `====== Version 2 ======` 到 `====== Version 5 ======`；`max_versions=3` 要等**下一次写入**才触发裁剪，届时 `oldest_version` 会变成 3（只剩 Version 3–5）。

三个值得配的字段：

- `max_versions=3`：只保留最近 3 个版本，避免历史无限增长；
- `cas_required=true`：所有写入必须带 cas；
- `delete_version_after=24h`：**版本到期自动软删除**（对"日志类密钥"很有用）。

`custom_metadata` 可以打业务标签，配合自动化做"这个密钥属于哪个团队/何时轮换"：

```bash
vault kv metadata put -mount=app -custom-metadata=owner=payments -custom-metadata=rotate_every=30d demo
```

### 4.7 列表：`list` 只列 key，不列值

```bash
vault kv put -mount=app db/prod password=p1
vault kv put -mount=app db/dev password=d1
vault kv list -mount=app
vault kv list -mount=app db
```

```text
Keys
----
db/
demo

Keys
----
dev
prod
```

`list` 对应 API 的 `LIST /v1/app/metadata/<path>`——所以**要让别人能列出目录，需要给 `metadata/` 路径的 `list` 能力**，而不是 `data/` 路径。这是第 5 章的重点之一。

## 原理：KV v2 为什么这么"啰嗦"

KV v2 相比 v1 多的那层 `metadata/`，本质是一个小的"版本控制数据库"：

```text
app/metadata/demo      ← 元数据：当前版本、保留策略、CAS 要求、自定义标签
app/data/demo          ← 指针：默认读到 current_version
app/data/demo?version=1 ← 读指定历史版本
app/delete/demo        ← 软删除标记（deletion_time）
app/destroy/demo       ← 物理抹除
```

三个必须记住的设计后果：

1. **写入路径和读取路径都带 `data/`**，但列出目录走 `metadata/`。策略里两套都要给。
2. **软删除是"标记"不是"删除"**，所以它可恢复、也会占用存储；真正清理要靠 `destroy` 或 `max_versions` 滚动淘汰。
3. **`destroy` 是不可逆的**，在生产脚本里执行前请当作 `rm -rf` 对待（Vault 的 `sudo` 能力与 `sys/` 端点可以帮助你做二次确认，见第 5 章）。

## 踩坑与检查清单

- **`put` 会覆盖整个 secret。** 只改一个字段请用 `patch`，或者干脆每次 `put` 时写全所有字段。
- **`get` 在版本被软删除时返回 0 且没有 Data 段。** 别用"输出长度"判断存在性，用 `-format=json` 检查 `data.data` 是否存在，或检查 `metadata.deletion_time`。
- **`undelete`/`destroy` 的参数是复数 `-versions=`**，而 `kv get` 是单数 `-version=`。写错会被参数校验拦下。
- **`destroy` 之后再 `undelete` 没有意义**：`destroyed: true` 的版本永远不会恢复。
- **想让"谁能列目录"和"谁能读值"分离**：`list` 只给 `metadata/` 的 `list`，读值给 `data/` 的 `read`。第 5 章有完整策略示例。
- **别把 KV v2 当数据库用。** 单条 secret 承载几十 KB 以上的内容会让读写和审计日志都变笨重（Vault 也有请求体大小上限）；超大对象请存对象存储，只把**密钥/凭据**放进 Vault。
- **dev 模式重启数据全丢**，练习时如果需要保留，用第 14 章的非 dev 配置。

有了能版本化的柜子，下一个问题自然就是：**谁有钥匙？** 这就是第 5 章。
